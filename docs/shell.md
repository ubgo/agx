# Shell layer

A program cannot change its parent shell's folder or environment. Two agx features need exactly that: moving your shell into the folder `agx new` or `agx resume` starts in, and setting a login for the current terminal. The shell layer is one small `agx()` function that does those two things and passes everything else straight through. It also defines one shell function per [alias](#aliases) and, with `--osc7`, tells your terminal which folder you are in.

You want it when you use `agx new` or `agx resume` (without it, the agent starts in the right folder but your shell stays where it was), when you switch logins per terminal, or when you want short commands such as `clw` for `agx run --profile work`. Every agx command works without it.

## Before you start

- agx on your `PATH` (the function calls the real binary as `command agx`).
- One of the supported shells: zsh, bash, fish or PowerShell (`pwsh`, on any OS). Other shells (tcsh, nushell, cmd) are refused: `--shell "tcsh": use one of zsh, bash, fish, pwsh` (exit 2).
- Nothing else: the layer reads aliases from your config, and still loads when the config is broken.

## Load it

Add one line to your shell's startup file, then open a new terminal:

```sh
eval "$(agx shell-init --shell zsh)"     # ~/.zshrc
eval "$(agx shell-init --shell bash)"    # ~/.bashrc
agx shell-init --shell fish | source     # ~/.config/fish/config.fish
```

For PowerShell, add this line to the file `$PROFILE` names:

```powershell
agx shell-init --shell pwsh | Out-String | Invoke-Expression
```

Add `--osc7` to any of them to also [report the folder to the terminal](#report-the-folder-to-the-terminal---osc7).

The layer is a short script you can read before you load it. This is the zsh one for a config with two aliases ([`examples/shell-init/config.jsonc`](../examples/shell-init/config.jsonc)); bash gets the same script:

<!-- snippet: examples/shell-init/session.txt#zsh -->
```sh
$ agx shell-init --shell zsh
# agx shell layer (zsh), generated by `agx shell-init --shell zsh`.
# Load it with: eval "$(agx shell-init --shell zsh)". Edit the config, not this output.
\builtin export AGX_SHELL=zsh

# The definitions below are parsed with your aliases switched off, then the
# setting is restored: the layer is eval'd in your shell, where an alias such
# as `alias do='cd ~/Downloads'` or `alias then=...` would break its parse (and
# with it every function) and `alias cd=...` would run instead of cd. zsh
# parses a whole eval at once, so the definitions are one quoted eval run
# after the switch. Your aliases still work everywhere else, and one named
# like a function here still wins when you type it.
__agx_aliases=${options[aliases]}
\builtin unsetopt aliases
\builtin eval '
# __agx_has FLAG ARGS...: whether ARGS hold FLAG or FLAG=... before a bare
# --. It recurses instead of looping, so the layer has no for/do/done at all.
__agx_has() {
  local __agx_f=$1
  shift
  [ $# -eq 0 ] && return 1
  case "$1" in
    --) return 1 ;;
    "$__agx_f"|"$__agx_f"=*) return 0 ;;
  esac
  shift
  __agx_has "$__agx_f" "$@"
}

# agx: one wrapper around the binary for the two things a child process
# cannot do for its shell. `new` and `resume` write a plan, cd to its folder,
# then start the agent from it; `login ... --terminal` sets AGX_LOGIN here.
# Everything else goes straight to the binary.
agx() {
  case "$1" in
    new|resume)
      local __agx_cmd __agx_plan __agx_dir __agx_rc
      __agx_cmd=$1
      shift
      __agx_plan=$(command mktemp "${TMPDIR:-/tmp}/agx-plan.XXXXXX") || return 125
      command agx "$__agx_cmd" --plan-file "$__agx_plan" "$@"
      __agx_rc=$?
      if [ "$__agx_rc" -ne 0 ] || [ ! -s "$__agx_plan" ]; then
        command rm -f -- "$__agx_plan"
        return "$__agx_rc"
      fi
      __agx_dir=$(command agx plan show --plan-file "$__agx_plan" --field data.dir) &&
        builtin cd -- "$__agx_dir" || {
        command rm -f -- "$__agx_plan"
        return 125
      }
      command agx launch --plan-file "$__agx_plan"
      __agx_rc=$?
      command rm -f -- "$__agx_plan"
      return "$__agx_rc"
      ;;
    login)
      local __agx_out __agx_rc
      if __agx_has --terminal "$@"; then
        __agx_out=$(command agx "$@")
        __agx_rc=$?
        case "$__agx_out" in
          "export AGX_LOGIN="*)
            export AGX_LOGIN="${__agx_out#"export AGX_LOGIN="}"
            builtin printf "%s\n" "agx: AGX_LOGIN=$AGX_LOGIN in this shell" >&2
            ;;
          "unset AGX_LOGIN")
            unset AGX_LOGIN
            builtin printf "%s\n" "agx: AGX_LOGIN unset in this shell" >&2
            ;;
          *)
            [ -n "$__agx_out" ] && builtin printf "%s\n" "$__agx_out"
            ;;
        esac
        return "$__agx_rc"
      fi
      command agx "$@"
      ;;
    *)
      command agx "$@"
      ;;
  esac
}
cl() { agx run --profile personal "$@"; }
clw() { agx run --profile work "$@"; }

'
\builtin test "$__agx_aliases" = on && \builtin setopt aliases
\builtin unset __agx_aliases
```

The fish script does the same with `set -gx` and `function agx --wraps agx`; the PowerShell one with `$env:` and `& $bin`, where `$bin` is the real `agx` executable. All four are in [`examples/shell-init/session.txt`](../examples/shell-init/session.txt). Because the config is read every time a shell starts, edit aliases in the config (or with `agx alias`), never in this output.

## What it does

| Feature | Without the layer | With it |
|---|---|---|
| `agx new`, `agx resume` | the agent starts in the right folder; your shell stays where it was | your shell also `cd`s there, then the agent starts; you are still there when it exits |
| `agx login use --id X --terminal` | prints `export AGX_LOGIN=X` to copy | sets `AGX_LOGIN` in this shell and says so (`agx: AGX_LOGIN=X in this shell`) |
| `agx login use --home-login --terminal` | prints `unset AGX_LOGIN` | unsets `AGX_LOGIN` (`agx: AGX_LOGIN unset in this shell`) |
| aliases from config | not defined | one shell function per alias |
| `agx doctor` | `shell layer not loaded` (info) | `shell layer loaded (zsh)` |
| everything else | runs agx | runs agx (the function calls `command agx`) |
| a layer made with `--config X` | each command needs its own `--config X` | every command and alias runs against X; a `--config` you type before a bare `--` wins, so the binary never sees two |

A layer made with the global `--config X` runs every command and alias against X. In bash and zsh one helper adds it to every call; fish and PowerShell do the same inside the wrapper. A `--config` you type before a bare `--` wins, and one after `--` belongs to the agent:

<!-- snippet: examples/shell-init/config.session.txt#config-helper -->
```sh
# __agx_bin runs the binary with the config of this layer, --config ~/.agx/config.jsonc,
# unless the arguments already name one before a bare --: the one typed
# wins, so the binary never sees --config twice.
__agx_bin() {
  if __agx_has --config "$@"; then
    command agx "$@"
    return
  fi
  command agx --config ~/.agx/config.jsonc "$@"
}
```

## How the `cd` works: the plan file

For `new` and `resume`, the function runs agx in three steps. You never type these commands (they are hidden), but you can run them by hand to see each step:

1. `agx new … --plan-file F` (or `agx resume … --plan-file F`) resolves every decision exactly like `--dry-run`, creates the session folder of `agx new`, writes the plan to `F` (a private temporary file from `mktemp`, mode 0600) and starts nothing. Notes and warnings print now.
2. `agx plan show --plan-file F --field data.dir` prints the folder; the function `cd`s there.
3. `agx launch --plan-file F` re-checks the plan, deletes it, resolves the secrets and starts exactly the planned agent.

<!-- snippet: examples/shell-plan-file/session.txt#plan -->
```sh
$ agx new --name "pglite golang" --plan-file ~/plan.json
agx: agent claude (default_agent)
agx: warning: installed Claude Code version unknown; flags not checked

$ agx plan show --plan-file ~/plan.json
mode     new
dir      ~/.agx/sessions/pglite_golang_20261118_061153
agent    claude
profile  personal
home     ~/.claude
login    home
binary   /usr/local/bin/claude
command  claude

$ agx plan show --plan-file ~/plan.json --field data.dir
~/.agx/sessions/pglite_golang_20261118_061153
```

<!-- snippet: examples/shell-plan-file/session.txt#launch -->
```sh
$ agx launch --plan-file ~/plan.json
agent claude
argv
pwd ~/.agx/sessions/pglite_golang_20261118_061153
...

$ agx launch --plan-file ~/plan.json
agx: plan file ~/plan.json does not exist
[exit 125]
```

A plan is single use (the second `launch` above finds nothing), and it never holds a resolved secret: `login home` or a login name, never a token. Every choice is pinned in the plan, so step 3 runs no picker, no auto-pick and no binding again. A plan older than 60 seconds, from the future, owned by another user or writable by others is refused, so a left-over or planted file cannot steer a launch (the example's `old-plan.json` was written long ago):

<!-- snippet: examples/shell-plan-file/session.txt#stale -->
```sh
$ agx plan show --plan-file ~/old-plan.json
agx: plan file is older than 60s or not yours
[exit 1]

$ agx launch --plan-file ~/old-plan.json
agx: plan file is older than 60s or not yours
[exit 125]
```

## Set `AGX_LOGIN` in this shell

`agx login use --terminal` checks the login and prints one line for the shell. Without the layer you copy it; with the layer the function matches exactly these two shapes and sets or unsets the variable itself (it never `eval`s agx output, so no output can run as code). The same two lines work for fish and PowerShell, because the function translates them. See [logins](logins.md) for what `AGX_LOGIN` decides.

<!-- snippet: examples/shell-plan-file/terminal.session.txt#login-terminal -->
```sh
$ agx login use --id carol --terminal
export AGX_LOGIN=carol

$ agx login use --home-login --terminal
unset AGX_LOGIN
```

With the layer, the first command prints `agx: AGX_LOGIN=carol in this shell` and every later `agx run` in this terminal uses `carol`, until `agx login use --home-login --terminal` (`agx: AGX_LOGIN unset in this shell`).

## Check it is loaded: `AGX_SHELL`

The layer exports `AGX_SHELL` with the shell's name (`zsh`, `bash`, `fish` or `pwsh`). `agx doctor` reads it; nothing else does, and no launch decision depends on it. Not loaded is information, never a failure:

<!-- snippet: examples/shell-plan-file/terminal.session.txt#doctor -->
```sh
$ agx doctor
...
· shell                  shell layer not loaded: new and resume leave this shell where it is
                         fix: eval "$(agx shell-init --shell zsh)"
...

$ AGX_SHELL=zsh agx doctor
...
✓ shell                  shell layer loaded (zsh)
...
```

## Report the folder to the terminal: `--osc7`

Terminals such as WezTerm, kitty, Ghostty, iTerm2 and the macOS Terminal open a new tab in the folder the shell last reported with the OSC 7 escape sequence. Many shells report it at each prompt; the agent replaces your prompt until it exits, so a new tab opened while the agent runs would start in the old folder. With `--osc7`, the function reports the new folder right after its `cd`, before the agent starts:

```sh
eval "$(agx shell-init --shell zsh --osc7)"
```

It adds one function to the script and calls it after the `cd` (`__agx_osc7` in the [full script](../examples/shell-init/osc7.session.txt)):

<!-- snippet: examples/shell-init/osc7.session.txt#osc7-function -->
```sh
# Report the current folder to the terminal (OSC 7) so new tabs open there.
__agx_osc7() {
  builtin printf "\033]7;file://%s%s\033\\\\" "${HOSTNAME:-$(command hostname)}" "$PWD"
}
```

Leave it off when your terminal does not understand OSC 7 or your prompt already reports it.

## Aliases

Aliases are named-flag agx arguments kept in config. The layer turns each into a shell function, so `clw` runs `agx run --profile work` and `clw --model opus` adds to it. Add, replace, list and remove them with `agx alias` (the config is edited in place, comments kept):

<!-- snippet: examples/shell-aliases/session.txt#add -->
```sh
$ agx alias add --name clw --args "run --profile work"
alias clw = agx run --profile work

$ agx alias add --name clr --args "resume --last"
alias clr = agx resume --last

$ agx alias add --name clw --args "run --profile work --model opus"
alias clw = agx run --profile work --model opus (was: agx run --profile work)

$ agx alias list
NAME  ARGS
clr   resume --last
clw   run --profile work --model opus
```

Or write them in the config:

<!-- snippet: examples/shell-init/config.jsonc#aliases -->
```jsonc
  "aliases": {
    "cl": "run --profile personal",
    "clw": "run --profile work"
  }
```

Open a new shell (or load the layer again) and the functions are there. In zsh and bash:

<!-- snippet: examples/shell-init/session.txt#zsh-aliases -->
```sh
cl() { agx run --profile personal "$@"; }
clw() { agx run --profile work "$@"; }
```

fish and PowerShell:

<!-- snippet: examples/shell-init/session.txt#fish-aliases -->
```fish
function cl --wraps 'agx run --profile personal'
    agx run --profile personal $argv
end
function clw --wraps 'agx run --profile work'
    agx run --profile work $argv
end
```

<!-- snippet: examples/shell-init/session.txt#pwsh-aliases -->
```powershell
function cl { agx run --profile personal @args }
function clw { agx run --profile work @args }
```

Each function calls the `agx` function, so an alias of `new` or `resume` also `cd`s. What `clw --model opus` runs is what you would type in full; preview it with `--dry-run`:

<!-- snippet: examples/shell-aliases/session.txt#dry-run -->
```sh
$ agx run --profile work --model opus --dry-run --quiet
agent    claude                                 from profile work
profile  work                                   from --profile
home     ~/.claude-work                         from profile work
login    home login                             from default (no login named)
binary   /usr/local/bin/claude version unknown  from no install metadata
folder   ~/projects/app                         from current folder
options  model=opus                             from --model
run      ~/.agx/runs/20261118-061207-bqpg       from AGX_RUN_ID=20261118-061207-bqpg
command  claude --model opus                    from built by agentio
env      set AGX_RUN_ID=20261118-061207-bqpg    from launch environment
         set AGX_RUN_AGENT=claude               from launch environment
         set AGX_RUN_PROFILE=work               from launch environment
         set AGX_RUN_LOGIN=home                 from launch environment
         set AGX_RUN_HOME=~/.claude-work        from launch environment
         set CLAUDE_CONFIG_DIR=~/.claude-work   from launch environment
note     installed Claude Code version unknown; flags not checked
```

An alias value is checked when you add it, when the config loads and by `agx config check`: it starts with an agx command (never a group such as `profile`, never a hidden one such as `launch`), every later word is a named flag of that command or its value, and `--` passes the rest to the agent. Values may only hold letters, digits, spaces and `_./:=@+-`, so an alias can never smuggle shell syntax into your shell:

<!-- snippet: examples/shell-aliases/session.txt#refusals -->
```sh
$ agx alias add --name x --args "run --profile work; rm -rf ~"
agx: --args: "run --profile work; rm -rf ~" has a character outside [A-Za-z0-9 _./:=@+-]
[exit 2]

$ agx alias add --name x --args "run work"
agx: --args: unexpected word "work"; every input is a named flag (see agx run --help)
[exit 2]

$ agx alias add --name x --args "profile"
agx: --args: agx profile needs a verb (add, edit, import, list, remove, show, use)
[exit 2]

$ agx alias add --name x --args "launch --plan-file f"
agx: --args: agx launch is internal; an alias cannot run it
[exit 2]

$ agx alias add --name x --args "run --nosuch"
agx: --args: agx run has no flag --nosuch
[exit 2]

$ agx alias remove --id nosuch
agx: unknown alias nosuch
  agx alias list
[exit 1]
```

`agx alias remove --id` deletes one:

<!-- snippet: examples/shell-aliases/session.txt#remove -->
```sh
$ agx alias remove --id clr
removed alias clr (agx resume --last)

$ agx alias list
NAME  ARGS
clw   run --profile work --model opus
```

## Completion

`agx completion` prints a completion script for commands and flags. Load it from the same startup file, after the shell layer:

```sh
eval "$(agx completion --shell zsh)"                       # ~/.zshrc, after compinit
eval "$(agx completion --shell bash)"                      # ~/.bashrc (needs the bash-completion package)
agx completion --shell fish | source                       # ~/.config/fish/config.fish
```

```powershell
agx completion --shell pwsh | Out-String | Invoke-Expression   # $PROFILE
```

It completes command names and flag names (with their help), not flag values such as profile names. It works with the shell layer loaded: the zsh and bash scripts complete the name `agx`, which the function keeps, and the fish function declares `--wraps agx`.

<!-- snippet: examples/shell-init/completion.session.txt#completion -->
```sh
$ agx completion --shell zsh
#compdef agx
compdef _agx agx
...

$ agx completion --shell bash
# bash completion V2 for agx -*- shell-script -*-
...

$ agx completion --shell fish
# fish completion for agx -*- shell-script -*-
...

$ agx completion --shell pwsh
# powershell completion for agx -*- shell-script -*-
...
```

## Your own aliases and functions

The layer is loaded into your shell after your own rc file, so it is written to survive what you keep there:

- **bash and zsh:** the definitions are parsed with alias expansion switched off, and the setting is put back right after. Aliases such as `alias do='cd ~/Downloads'`, `alias then=…` or `alias fi=…` used to break the whole layer at parse time (a `syntax error` or `parse error` on load, and then no `agx` function at all). zsh parses a whole `eval` at once, so the definitions are one quoted `eval` that runs after the switch; that is why the bash and zsh layers wrap their functions in `\builtin eval '…'`. The layer also has no `for … do … done` loop left.
- **Every shell:** the commands the layer runs itself are called as `builtin cd`, `builtin printf`, `command rm`, `command mktemp` and `command hostname` (fish the same; PowerShell by module-qualified names such as `Microsoft.PowerShell.Management\Set-Location`), so an alias or function of yours named `cd`, `printf` or `rm` is never run in their place.
- An alias of yours with the same name as an alias in agx's config still wins when you type it, as aliases always win over functions: remove one of the two if you want the other.

## Pitfalls

- After upgrading agx, open a new terminal (or load the layer again). A layer from an older build may write a plan the new binary refuses: `plan file schema_version N, this agx reads M; reload the shell layer (agx shell-init)`.
- PowerShell consumes a bare `--` when calling a function, so raw args to the agent need it quoted, as the pwsh script itself warns:

<!-- snippet: examples/shell-init/session.txt#pwsh-raw-args -->
```powershell
# PowerShell consumes a bare -- when calling a function: quote it ('--') to
# pass arguments through to the agent.
```

```powershell
agx run --profile work '--' --verbose
```

- A broken config never breaks your shell: shell-init prints the wrapper without aliases and a warning on stderr, while every other command refuses the config (exit 2):

<!-- snippet: examples/shell-aliases/broken.session.txt#broken -->
```sh
$ agx shell-init --shell zsh --config ~/broken.jsonc
agx: warning: config not loaded, no aliases: broken.jsonc:9:5: "run --profile personal; rm -rf ~" has a character outside [A-Za-z0-9 _./:=@+-]
# agx shell layer (zsh), generated by `agx shell-init --shell zsh --config ~/broken.jsonc`.
...

$ agx profile list --config ~/broken.jsonc
agx: broken.jsonc:9:5: "run --profile personal; rm -rf ~" has a character outside [A-Za-z0-9 _./:=@+-]
[exit 2]
```

- `agx alias add` refuses the names `agx`, `command`, `builtin`, `cd`, `set` and `function` (exit 2): the layer will not define a function that replaces its own wrapper or a shell builtin. An alias with such a name written into the config by hand is refused when the config loads, with its line and column, for every command (exit 2); shell-init warns and still prints the wrapper, without aliases. Pick another name.

<!-- snippet: examples/shell-aliases/reserved.session.txt#reserved -->
```sh
$ agx alias add --name agx --args "run --profile work"
agx: --name "agx": a name may not be agx, command, builtin, cd, set, function
[exit 2]

$ agx shell-init --shell zsh --config ~/reserved.jsonc
agx: warning: config not loaded, no aliases: reserved.jsonc:8:5: alias "agx": a name may not be agx, command, builtin, cd, set, function
# agx shell layer (zsh), generated by `agx shell-init --shell zsh --config ~/reserved.jsonc`.
...
```

- An alias word starting with `=` (zsh expands `=word` to a path) or `@` (PowerShell splats `@word`) is refused by `agx alias add` the same way, and refused at load (line:col) when written by hand.
- When the function cannot make the plan file, read it back or `cd` into the folder, it returns 125 (agx failed before the agent started) and removes the plan.
- Only `new` and `resume` move your shell. `agx run --dir ~/x` starts the agent in `~/x` and leaves your shell where it is.
- `--shell` is required for `shell-init` and `completion`: `--shell is required: one of zsh, bash, fish, pwsh` (exit 2).
